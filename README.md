<h1>🏗️ ИИ-ассистент отдела продаж стройматериалов</h1>

<p>Telegram-бот с архитектурой SQL-RAG, который автоматически консультирует клиентов по наличию, ценам и логистике, строго соблюдая 152-ФЗ и исключая галлюцинации ИИ в финансовых расчётах.</p>

<p><strong>Рабочее название:</strong> StroyBot<br>
<strong>Полное название из ТЗ:</strong> Умный помощник отдела продаж стройматериалов<br>
<strong>Канал:</strong> Telegram<br>
<strong>LLM:</strong> GigaChat (Сбер)</p>

<h2>💼 О проекте и бизнес-ценность</h2>

<p>Торгово-дистрибьюторская компания теряла «горячие» лиды из-за долгого ответа менеджеров (до 12 часов) и тратила до 40% времени на рутинные расчёты.</p>

<p>StroyBot решает эти проблемы:</p>
<ul>
  <li><strong>Скорость и конверсия:</strong> Время первичного ответа сокращено с 2–12 часов до < 15 секунд (24/7), что предотвращает потерю «горячих» лидов.</li>
  <li><strong>Нулевые галлюцинации:</strong> Архитектура запрещает LLM считать математику. Все цены, остатки и стоимость доставки извлекаются точными SQL-запросами. ИИ только формирует вежливый ответ на основе готовых цифр.</li>
  <li><strong>Безопасность и 152-ФЗ:</strong> Гибридная гео-архитектура (n8n в Амстердаме для доступа к API, PostgreSQL в Москве для хранения ПДн). Реализовано автоматическое маскирование идентификаторов (например, <code>174****684</code>) перед записью в логи.</li>
  <li><strong>Умный поиск с опечатками:</strong> Использование расширений PostgreSQL (<code>pg_trgm</code> и полнотекстовый поиск) позволяет корректно распознавать запросы вроде "ашгабад" или "цемет" и находить нужные правила доставки и товары.</li>
</ul>

<h2>🏗️ Архитектура и технологический стек</h2>

<p>Проект использует <strong>гибридную гео-архитектуру</strong> для баланса между доступностью API и безопасностью данных:</p>

<ul>
  <li><strong>Интерфейс:</strong> Telegram Bot API</li>
  <li><strong>Оркестратор:</strong> n8n (Self-hosted, сервер в Амстердаме) — управляет пайплайном, логикой ветвления и вызовами API</li>
  <li><strong>Хранилище данных:</strong> PostgreSQL (сервер в Москве, РФ) — хранит прайс-листы, правила доставки, клиентов и замаскированные логи диалогов</li>
  <li><strong>Языковая модель:</strong> GigaChat (Сбер) — генерация ответов на русском языке, данные не покидают контур РФ</li>
  <li><strong>Инфраструктура:</strong> VPS Timeweb Cloud (Амстердам + Москва), Docker, Nginx</li>
</ul>

<h2>✨ Ключевые фичи StroyBot</h2>

<ul>
  <li><strong>SQL-RAG вместо Vector-RAG для цен:</strong> Для структурированных данных (прайс, остатки) используется точный SQL-поиск, что гарантирует 100% точность и исключает галлюцинации LLM.</li>
  <li><strong>Умный поиск с опечатками:</strong> Использование <code>pg_trgm</code> и полнотекстового поиска PostgreSQL позволяет находить товары и города доставки даже при опечатках (например, "ашгабад" → "Ашхабад, Туркменистан").</li>
  <li><strong>База синонимов городов:</strong> Таблица <code>city_synonyms</code> содержит 500+ вариантов написания городов РФ и СНГ для корректного распознавания доставки.</li>
  <li><strong>Безопасность 152-ФЗ:</strong> Реализовано маскирование <code>chat_id</code> (например, <code>174****684</code>) в ноде <code>Code</code> перед записью в таблицу <code>dialogue_logs</code>.</li>
  <li><strong>Fallback-сценарии:</strong> При нестандартных запросах или запросах на раскрытие ПДн бот корректно передает диалог менеджеру.</li>
  <li><strong>Разделение опт/розница:</strong> Автоматическая проверка типа клиента и применение соответствующих цен (оптовые цены — только для авторизованных дистрибьюторов).</li>
</ul>

<h2>⚠️ Архитектурное решение: Почему SQL-RAG, а не Vector-RAG?</h2>

<blockquote>
<p>В классических RAG-системах для поиска используется векторное сходство (эмбеддинги). Однако для <strong>структурированных финансовых данных</strong> (цены, остатки на складе, точные тарифы) векторный поиск неприменим, так как он ищет "семантически похожее", а не "точное". Попытка использовать LLM для расчета стоимости на основе векторных чанков неизбежно ведет к галлюцинациям.</p>
<p><strong>Решение в проекте:</strong> Реализован гибридный подход. Для неструктурированных правил (текст регламента) используется полнотекстовый поиск PostgreSQL. Для цен и остатков — строгие SQL-запросы (<code>ILIKE</code>, <code>pg_trgm</code>). n8n выступает в роли "калькулятора", собирая точные цифры и передавая их в GigaChat только для форматирования ответа. Это гарантирует 100% точность расчетов.</p>
</blockquote>

<h2> Оценка стоимости владения (TCO)</h2>

<p>На основе реального логирования (<code>tokens_used</code> в таблице <code>dialogue_logs</code>):</p>
<ul>
  <li>Средний расход на 1 запрос: ~460–520 токенов (входной промпт + контекст + ответ)</li>
  <li>Стоимость API GigaChat: ~0.46 руб. за запрос</li>
  <li>При нагрузке 100 запросов/день: API ≈ 1 380 руб./мес + Инфраструктура (2 VPS) ≈ 800 руб./мес</li>
  <li><strong>Итоговый TCO:</strong> ~2 200 – 2 600 руб./мес (с запасом 20%)</li>
</ul>
<p><em>Вывод: Решение экономически эффективно и окупается за счет высвобождения 1.5 часов рабочего времени менеджера в день.</em></p>
